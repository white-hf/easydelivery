# 地图空屏补偿需求文档

## 背景
司机在驾驶派送过程中，当前地图跟随视图整体体验较好，能够根据运动路线展示附近包裹。  
但存在一个真实边缘问题：有时当前屏幕核心区域内一个包裹都没有，而最近包裹其实只在屏幕外不远处。此时司机通常会手工缩放或拖动地图，确认下一个包裹的大概方向。

这个问题是一个低频但真实的驾驶辅助需求。目标不是重新设计地图主视图，而是在不破坏现有驾驶跟随体验的前提下，替代司机做一次轻量查看动作。

## 产品目标
- 当正常驾驶视图核心区域内没有包裹，且最近包裹只在屏幕外不远时，系统提供一次轻量镜头补偿，让司机快速知道包裹位置。
- 补偿动作完成后，立即回到现有运动跟随逻辑，不进入持续 rescue 模式。
- Android 和 iOS 两端行为保持一致。

## 非目标
- 不追求驾驶中始终显示下一个包裹。
- 不做长期 zoom out。
- 不修改正常驾驶中的聚合规则。
- 不在高速巡航、远距离候选、或多目标冲突场景下主动控制镜头。
- 不替代当前主跟随逻辑，只做一次性补偿。

## 方案选择
本需求采用 `方案 3：一次性镜头移动到旁边包裹`。

不采用另外两种方案的原因：
- `持续 rescue 状态机`
  - 行为复杂，容易导致镜头持续调整。
  - GPS 抖动、目标切换、屏幕边缘进出都会带来不可预测体验。
- `轻微缩放 + 临时降低聚合`
  - 需要同时改相机和 cluster 规则。
  - 容易让司机感知到地图语义变化，出现“为什么这时散开、那时又聚合”的不稳定体验。

## 用户故事
- 作为司机，当当前驾驶视图里没有包裹，但最近包裹就在前方或侧前方不远处时，我希望系统替我做一次轻量查看动作，让我知道它大概在哪，而不是我自己去缩放地图。

## 触发原则
系统只在以下条件同时满足时触发一次空屏补偿：

1. 当前处于地图驾驶跟随状态。
2. 当前核心可视区内没有包裹。
3. 存在一个稳定的最近包裹候选。
4. 该候选位于当前屏幕外，但距离屏幕边界不远。
5. 用户最近没有手势拖图、缩放、点击恢复跟随等交互。
6. 当前不属于高速巡航场景。

## 交互定义

### 1. 核心可视区
为避免包裹刚贴边也被认为“已可见”，地图应定义一个比实际屏幕更小的核心可视区。

建议：
- 屏幕四周内缩 10% 到 15%。
- 只有核心可视区内 0 个包裹时，才允许触发补偿。

### 2. 候选包裹
候选包裹不是任意最近包裹，而是满足以下优先级的目标：
- 当前主 focus 包裹优先。
- 若没有主 focus，则选最近且方向上更符合当前前进路径的包裹。
- 已经触发过补偿且随后进入过屏幕的包裹，不再次作为候选。

### 3. 镜头动作
触发后系统执行一次轻量镜头平移：
- 尽量保持当前 `bearing`、`tilt`、主要 zoom 语义不变。
- 优先只平移 camera target，不做明显 zoom 变化。
- 目标是把候选包裹带入屏幕前方或侧前方边缘，而不是把镜头跳到包裹中心。

### 4. 补偿后行为
- 补偿动作执行一次后，立即回到现有跟随逻辑。
- 不持续追踪该包裹。
- 不因为补偿而改变后续正常 driving follow 的相机策略。

## 场景边界

### 应触发场景
- 低速驾驶。
- 当前核心可视区内没有包裹。
- 最近包裹就在屏幕外不远，司机本来很可能会手工缩放看一下。

### 不应触发场景
- 最近包裹距离过远，例如 2km 级别。
- 当前屏幕核心区内已经至少有一个包裹。
- 高速巡航。
- 公寓/市中心密集区域，即使移动镜头也大概率只会看到 cluster。
- 最近候选在司机后方或明显不是当前行进方向上的有效目标。
- 用户刚手动拖图或缩放。

## 主要体验风险与防护

### 风险 1：镜头自己乱跳
防护：
- 只做一次性补偿，不做持续 rescue。
- 必须满足核心区 0 包裹。
- 同一目标包裹不重复触发。

### 风险 2：路过包裹时反复触发
典型轨迹：
- 屏幕外 -> 屏幕内 -> 屏幕外

防护：
- 包裹一旦曾因补偿进入屏幕，不再为同一包裹重复触发。
- 如果司机已开始远离该包裹，不再次触发。

### 风险 3：选中数学上最近、但体验上错误的包裹
防护：
- 候选目标不能只按直线距离选取。
- 应结合当前 focus、前进方向、是否已路过等因素排序。

### 风险 4：用户主动操作与系统自动操作冲突
防护：
- 发生地图手势后，短时间内不触发自动补偿。
- 用户恢复自动跟随前，不再次主动移动镜头。

## 建议实现拆分

### 第 1 阶段
- 增加“核心可视区内是否有包裹”的可靠判断。
- 增加“屏幕外不远候选包裹”的筛选逻辑。
- 增加一次性镜头平移补偿能力。

### 第 2 阶段
- 补充目标去重和已路过目标过滤。
- 补充日志与埋点，观察真实触发频率与司机反馈。

## 验收标准

1. 正常驾驶时，如果屏幕核心区内已经有包裹，镜头行为与当前版本保持一致。
2. 当核心区内没有包裹，且最近包裹只在屏幕外不远时，系统最多执行一次轻量补偿，把包裹带入视野。
3. 补偿后镜头应回到当前既有运动逻辑，不持续跟随该补偿目标。
4. 同一包裹在“屏幕外 -> 屏幕内 -> 屏幕外”的路过场景下，不应反复触发补偿。
5. 用户发生地图手势操作后，系统不应再主动抢镜头。
6. Android 与 iOS 的触发条件、动作方向、退出方式保持一致。

## 埋点与日志建议
- 记录是否命中“核心区 0 包裹”。
- 记录候选包裹 id、与屏幕边界的相对位置、与当前 focus 的关系。
- 记录补偿是否触发、是否成功把包裹带入视野。
- 记录用户在补偿前后是否又立刻手势调整地图。

## 当前结论
这是一个真实但低频的辅助需求。  
产品上应坚持“轻量、一次性、低侵入”，不能再把它扩展成持续缩放或长期主动控制相机的逻辑。
